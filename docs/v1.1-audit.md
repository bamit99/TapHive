# TapHive v1.1 — Audit & Hardening Findings

Date: 2026-11-26  
Baseline commit: `57c8f79` (`Align README with v1.0 features`)  
Target: v1.1 engineering and security hardening

## Scope and method

Reviewed all 24 Kotlin sources, the manifest, resources, network-security policy, Gradle configuration, README/BUILDPLAN, and the current release/build outputs. Ran:

- `assembleDebug` — success
- `assembleRelease` — success, but produced `app-release-unsigned.apk`
- `testDebugUnitTest` — `NO-SOURCE` (no tests exist, so no tests ran)
- `lintDebug` — 0 errors, 40 warnings
- Device baseline: CPH2585 on Android 16 / API 36; no Android 13–15 device was connected during this audit

This report is intentionally written before code changes.

## Executive summary

The v1.0 implementation is functional and has a good small-app shape: a pure-Kotlin packet reader, one foreground VPN service, a bounded syslog queue, network-bound helper sockets, local SQLite history, and no third-party runtime dependencies.

It is **not ready for a v1.1 release** without changes. The most serious gaps are:

1. The published v1.0 APK is debuggable and debug-signed; `assembleRelease` is unsigned.
2. A malformed/fragmented packet can kill the packet loop while the VPN remains up, producing a silent device-wide network blackout.
3. External IP enrichment is enabled implicitly and uses cleartext HTTP.
4. Syslog has no TLS path and therefore cannot satisfy the v1.1 “no silent downgrade” requirement.
5. The TCP path can create phantom connections, ACK before delivery, and leak idle sessions/threads.
6. Network transitions (Wi-Fi ↔ cellular) are not handled after capture starts.
7. Android 16 back handling is dead because the app still uses `onBackPressed()` with targetSdk 36.
8. There are no automated tests.
9. Public screenshots currently expose real app and destination usage data.

## Remediation status (v1.1)

### Fixed in v1.1
- Malformed/fragmented packet containment and capture-failure teardown.
- UDP/TCP header validation, UDP session cleanup, DNS parser bounds/fuzz.
- TCP SYN gate, RST ACK correction, bounded write queue, idle expiry.
- Flow-counter atomics, throttled expiry.
- External enrichment explicit opt-in, HTTPS `ipwho.is`, response/queue/cache caps.
- TLS syslog with platform trust + hostname verification and fail-closed behavior.
- Android 16 back handling; data-extraction rules; non-exported TrafficActivity.
- Non-VPN network callback and `addDisallowedApplication`.
- SQLite v2 migration, WAL, indexes, off-thread writes, background TRAFFIC queries.
- Release signing/minification/non-debuggable build; v1.1 metadata.
- Public traffic screenshots removed; SIEM documentation and CHANGELOG added.

### Remaining / accepted for v1.2
- Successful TLS session against a system-trusted collector not yet lab-tested.
- No TLS pinning/mTLS.
- TCP retransmission/out-of-order/half-close remains simplified.
- IPv6 forwarding is still deferred.
- History remains plaintext inside the app sandbox.
- Android 13–15 device coverage missing.
- Audit report still contains pre-fix detail and is intentionally not public.

## Detailed notes

### 1. Privacy and security

**P-01/P-05/P-06 — enrichment consent and transport**

Current flow: `CaptureService.onFlowOpen()` calls `app.geoResolver.lookup(dstIp)` for every public destination, with no preference check. `IpGeoResolver` builds an HTTP request to `ip-api.com` and the network-security policy allows cleartext for that host.

Required v1.1 design:

- Add `enrichment_enabled` preference, default **off**.
- Add a visible setting: “External IP enrichment (HTTPS)” with a one-line disclosure that public destination IPs are sent to the provider.
- When off, make no network request; show DNS names (on-device) and `LOCAL`; leave country/org empty.
- Replace the HTTP provider with an HTTPS endpoint that supports certificate validation, or keep the provider switchable. A candidate is `ipwho.is` (`country`, `connection.org`, `connection.isp`, `connection.asn`); verify its current terms/rate limits before implementation.
- Remove the `ip-api.com` cleartext exception from `network_security_config.xml` once the HTTP path is gone.
- Send only the destination IP; never UID, ports, DNS name, app label, or flow history.

**P-02 — TLS syslog**

There is no `tls` transport in `Prefs`, settings UI, or `SyslogSender`. v1.1 should add TLS over TCP (typically port 6514):

- Use the platform default `SSLSocketFactory` and default trust store.
- Set endpoint identification (`HTTPS`) so certificate hostnames are verified.
- Bind the TLS socket to the underlying `Network` before connect.
- Treat handshake/certificate failure as a red target error.
- Do not fall back to TCP/UDP after a TLS failure. Keep cleartext UDP/TCP only as deliberate, separately labelled options.

**P-03 — stored history**

`android:allowBackup="false"` is present, but Android 12+ requires `android:dataExtractionRules` for cloud backup and device-to-device transfer. Add a rules resource excluding databases/preferences from both paths.

Encryption-at-rest is not implemented. If v1.1 requires protection against a rooted/backup-extracted device, evaluate SQLCipher or an explicit Keystore-backed encrypted store; otherwise document sandbox-only protection as a known limitation. Do not claim encryption that does not exist.

**P-07 — published APK integrity**

Artifact inspection of `dist/TapHive-1.0.apk` confirms:

```text
android:debuggable=true
Signer #1 certificate DN: C=US, O=Android, CN=Android Debug
SHA-256: 3a442409b7da52a854f3738959b10bed732af05f9c78665922a5ef23019c31af
```

A debuggable VPN/security app can be inspected with `run-as`, attached to with a debugger, and is not acceptable as a public release. The repository has no `signingConfigs`/`buildTypes` block, and `assembleRelease` produces `app-release-unsigned.apk`. Define a release keystore outside the repo, build a non-debuggable release, enable minification, verify v3/v4 signatures, and replace the GitHub asset. Do not treat the debug APK as the v1.1 release.

**P-08 — NSC is not a raw-socket control**

Android’s network-security config is not guaranteed to govern raw `Socket`/`DatagramSocket` traffic. TapHive uses raw sockets for both enrichment and syslog, so the `ip-api.com` exemption is documentation, not an enforcement boundary. Add a code-level cleartext policy (explicit acknowledgement per destination/transport) and use `HttpsURLConnection` for enrichment so the platform policy applies. Update the README claim accordingly.

**P-09 — enrichment resource limits**

`IpGeoResolver` uses an unbounded single-thread executor, unbounded `attemptedAt`/`countries` maps, and `readBytes()` on the response stream with no size cap. A malicious or broken endpoint can stream a large body within the 5-second timeout, and a burst of unique destinations can grow the queue/maps indefinitely. Cap the body (e.g. 64 KiB), bound/coalesce the queue, prune maps, validate/truncate labels, and disable redirects.

**P-10 — syslog write deadline**

The TCP/TLS sender thread performs blocking `write`/`flush` without a write deadline. A server that accepts the connection but stops reading can stall the single sender, fill the 512-slot queue, and drop all subsequent events. Add a watchdog/close-on-timeout and mark target health separately for “connected” versus “wrote successfully”.

**P-11/P-12/P-13 — low-severity hardening**

- Extend the local-IP filter to reserved, multicast, and IPv4-mapped IPv6 ranges; add range tests.
- Correlate DNS answers with recently issued queries or restrict to the system resolver; sanitize/cap labels and shorten the cache TTL.
- Correct README wording: “TCP connect succeeded” is not authenticated listener proof; NSC does not bind raw sockets; enrichment has a 6-hour lookup suppression and a 30-day metadata cache; `allowBackup=false` does not fully control device-to-device transfer.

**P-04 — screenshots**

`02-traffic-applications.png` and `03-traffic-destinations.png` show real app names, UIDs, IP addresses, organisations, countries, and traffic volumes. This is sensitive behavioural metadata in a public repository. Replace them with controlled demo data before v1.1 publication.

### 2. Network and protocol reliability

**N-01/N-07 — malformed UDP and escaped exceptions**

`Ipv4TunnelForwarder.forward()` checks only `totalLength > headerLength` before doing:

```kotlin
val payload = raw.copyOfRange(headerLength + 8, totalLength)
```

A truncated UDP header (length between `headerLength + 1` and `headerLength + 7`) passes the earlier checks and throws `IllegalArgumentException`. `PacketReader` does not catch exceptions around `forwarder?.forward(...)`, so the packet loop can terminate.

Remediation: validate `headerLength + 8 <= totalLength` for UDP, `totalLength >= needed` for TCP, wrap forwarding in a guarded boundary, and fail closed per packet rather than per capture session.

**N-02 — UDP session cleanup**

`UdpSession.receiveLoop()` breaks on `SocketException`/`IOException` but never calls `closeSession()`. The session remains in `sessions`, the socket may be closed, and a later `send()` can throw. Always remove the session in a `finally` block.

**N-03 — network transitions**

`Networks.underlying()` uses `allNetworks.firstOrNull(...)`, which is deprecated and may select the wrong network when both Wi-Fi and cellular are present. The selected network is assigned once in `CaptureService.startCapture()`; `SyslogSender` and `IpGeoResolver` keep that reference. When the network changes, sockets continue using the old network.

Remediation: use `ConnectivityManager` callbacks / `registerDefaultNetworkCallback`, select the validated non-VPN default, and re-bind or recreate helper sockets/sessions on change. Track network changes in the target-health state.

**N-04 — TCP proxy limits**

The current TCP path:

- ignores gaps and relies on client retransmission (`acceptPayload`)
- sends server data once and never retransmits unacknowledged bytes
- does not reassemble server-side out-of-order data
- has no explicit established-idle timeout
- sends a simplified RST/FIN sequence
- relies on a 65535 window without scaling

This is acceptable only for a best-effort local proxy on a reliable tun. It must be documented or replaced with a bounded state machine with retransmission/ack tracking before claiming robust TCP forwarding.

**N-05 — thread/session explosion**

Every UDP flow starts a thread; every TCP flow starts a connector and reader thread. There is no cap. A device with many short-lived flows can create hundreds of threads and sockets. Add a max-session limit and a shared executor/selector-based design, or at minimum a bounded session table with eviction and metrics.

**N-06 — validation**

Neither parser validates IP checksums, TCP/UDP checksums, IP total length against captured length, or IPv4 fragment metadata. Non-first fragments are treated as ordinary transport packets. Decide whether the product is “best-effort metadata” (then document) or “safe forwarder” (then validate/reassemble).

**Critical failure cascade**

`PacketReader.loop()` calls `forwarder?.forward(...)` without a guard (`PacketReader.kt:132-135`). Several reachable paths throw:

- `UdpSession.send()` can race with the 60-second close and throw `SocketException` (`Ipv4TunnelForwarder.kt:77-80`).
- A truncated UDP header reaches `copyOfRange(headerLength + 8, totalLength)` (`:389`).
- A `DatagramSocket`/`Socket` constructor can fail under fd exhaustion (`:404`, `:453`).
- `vpn.protect()` or `network.bindSocket()` can fail (`:457-465`).

The packet thread then exits, `finally` clears the flow map, but `CaptureService.isRunning` remains true and the tun stays established. Because all IPv4 traffic is routed into the tun, the device loses connectivity while the notification still says capture is live. This is the highest-priority reliability bug: per-packet failures must be contained, the failing session evicted, and reader-thread death must tear down the service with a visible error.

IPv4 fragmentation is also absent. A large UDP datagram's trailing fragment has a short `totalLength` and hits the same `copyOfRange` crash; first fragments are forwarded as if complete, so large datagrams are silently truncated. Reject fragments (`MF` set or nonzero offset) or implement bounded reassembly before reading transport headers.

`DnsNameParser` has a separate boundary bug: `readName()` can legitimately return an offset at `length`, after which `parse()` reads `u16(payload, parsed.second)` and `u16(payload, parsed.second + 8)` (`DnsNameParser.kt:37-40`). A truncated response can throw `ArrayIndexOutOfBoundsException` inside `UdpSession.receiveLoop`, which catches only `IOException` (`Ipv4TunnelForwarder.kt:82-115`), killing the UDP receive thread and leaking the session. Bound-check every field read and catch parser failures inside the receive loop.

**TCP proxy hardening notes**

- Sessions are created for any unknown 4-tuple (`Ipv4TunnelForwarder.kt:372-379`); there is no SYN gate. After a normal close, the client's final ACK can create a new outbound connection with no data. Add a TIME_WAIT set and create sessions only for `SYN && !ACK`.
- Client data is ACKed before the protected socket accepts it; `outgoing` is an unbounded queue, and `closeSession()` clears it (`:138,203-213,347`). Advertise a window based on queue depth, bound the queue, and do not clear ACKed data without a reset.
- `sendRst()` uses `ack = 0` (`:195-201`); a peer may ignore it. Use `ack = clientIsn + 1` for a SYN response or the current receive-next value for established flows.
- There is no established-idle timeout and server EOF closes the session immediately (`:290-336`), so half-closed uploads truncate and dead peers leak two threads/socket per flow.
- UDP receive uses a 1472-byte buffer (`:83-103,591`); larger replies are silently truncated. Use 65535 and drop oversize replies explicitly.
- The TCP SYN-ACK advertises MSS 1360 but reads/emits up to 1460 (`:169,292,590`); cap reads to the advertised/peer MSS.
- `TunWriter` treats a short write as a remainder and can block forever holding the global lock (`TunWriter.kt:13-45`). Treat a partial write as an error and bound poll retries.
- The tun fd can be closed twice (`PacketReader.kt:83,91-94`, `CaptureService.kt:287-290`); own exactly one close.
- `startCapture()` and `releaseCapture()` need a single mutex/generation check; stop during `establish()` can leave an orphan VPN.
- Per-packet `expire()`/`sampleFlows()` plus `String.format` and `copyOfRange` allocations (`PacketReader.kt:130-140,242-304`) add avoidable hot-path cost; gate maintenance on a timer and reduce allocations.

**Android 16 back navigation (release blocker)**

Android’s Android 16 behavior-change documentation states that for apps targeting API 36, `onBackPressed()` is not called and `KeyEvent.KEYCODE_BACK` is not dispatched. TapHive targets 36 and uses `onBackPressed()` in both `MainActivity` and `TrafficActivity`, so the exit-confirm dialog and Traffic-to-Main back routing are dead on a current device. Migrate to `OnBackPressedDispatcher`/`OnBackInvokedCallback` (or temporarily opt out with `android:enableOnBackInvokedCallback="false"` while migrating, then remove the opt-out). Test with `pressBack()` on an API 36 image.

**Self-capture and helper sockets**

`CaptureService` can start with `network == null` if no non-VPN internet network is available at start. `SyslogSender` then skips `bindSocket()` and can send through the VPN it is trying to observe; `addDisallowedApplication(packageName)` is not set on the VPN builder. This can feed TapHive's own syslog/geo traffic back into capture. Protect helper sockets explicitly and fail visibly when no safe underlying network exists.

**Boot opt-in and process revival**

`TapHiveApp.onCreate()` starts capture whenever `captureWanted` is true, before `BootReceiver` can enforce `startAtBoot && captureWanted`. The boot opt-in is currently saved by the fact that VPN consent usually does not survive reboot, not by the app’s own logic. Remove the unconditional auto-start from `TapHiveApp`; rely on `MainActivity`’s explicit resume path and the service’s null-intent restart path.

**History-off behavior**

`TrafficDatabase.recordFlow()` respects `retentionHours <= 0`, but `upsertGeo()`/`upsertDnsName()` do not, and `IpGeoResolver.lookup()` still runs for every public destination. A user who turns history off still gets local metadata writes and third-party lookups. Gate both writes and lookups on retention/enrichment settings, and prune `ip_meta` from a scheduled task.

**IPv6 completeness**

The app routes only IPv4; IPv6 has no address or route and bypasses the tunnel. On dual-stack networks this is a capture gap and a leak-shaped expectation gap. Either implement v6 forwarding safely or surface “IPv6 not captured” in the UI and README; do not imply complete traffic coverage.

### 3. Concurrency and lifecycle

**C-01 — flow counters**

`Flow.bytesReceived` and `packetsReceived` are updated from forwarder reader threads via `recordInbound()` while the packet thread reads/samples them. Use `AtomicLong`/per-flow synchronization or route all updates through one thread.

**C-02 — main-thread stop**

`releaseCapture()` calls `reader.stop()`, which calls `forwarder.stop()` and `thread.join(2_000)` while holding the service lock. If invoked on the main thread, this can block for up to two seconds. Move teardown to a worker and signal completion, or join asynchronously.

**C-03/C-04 — SQLite on hot threads**

`onFlowBytes()` writes directly to SQLite on the packet thread; `TrafficActivity` queries the database on the main thread every second. Both should move behind a single-thread DB executor with bounded queuing and a coalesced UI refresh. This also makes “dropped history writes” explicit.

**C-05/C-06 — migration and indexes**

`onUpgrade()` drops both tables. v1.1 must add a real migration path before changing the schema. Add WAL, indexes for `flows(ts)`, `flows(uid)`, and the destination grouping path, and measure query time at 7-day retention.

**C-07 — flow count semantics**

`appRows()` and `topDestinations()` use `COUNT(*)`, but the table stores 10-second byte samples as well as close events. The displayed “flows” count is therefore a row count, not a flow count. Add a persisted flow identifier/close record or rename the UI metric.

## SIEM compatibility notes

The v2 JSON contract is usable by all three targets, but each needs a small parser because the JSON is carried inside a syslog message rather than emitted as a bare JSON line.

| Field | Type | Splunk | Elastic | Sentinel |
| --- | --- | --- | --- | --- |
| `th_timestamp` | ISO-8601 string | `TIME_PREFIX`/`TIME_FORMAT` or JSON extraction | `date` mapping, `ISO8601` | `datetime` in DCR/table |
| `th_session_id` | string | dimension | `keyword` | `string` |
| `th_flow_id` | string | correlation key | `keyword` | `string` |
| `th_event` | string | `flow_open`/`flow_close`/lifecycle | `keyword` | `string` |
| `th_uid` | integer | numeric | `long` | `int`/`long` |
| `th_protocol` | integer | 6/TCP, 17/UDP | `integer` | `int` |
| `th_src_ip`/`th_dst_ip` | string | `ip` | `ip` | `string` |
| `th_src_port`/`th_dst_port` | integer | numeric | `integer` | `int` |
| `th_bytes_*`/`th_packets_*` | long | numeric | `long` | `long` |
| `th_status` | string | flow close status | `keyword` | `string` |

Planned examples:

- **Splunk:** UDP/TCP 514 input, `sourcetype=taphive:syslog`, line breaking on newline, regex/`spath` extraction of the JSON tail, and a saved search joining `flow_open` to `flow_close` on `th_session_id + th_flow_id`.
- **Elastic/ELK:** Filebeat/Logstash syslog input, grok the RFC 3164/5424 header, `json` filter on the MSG field, index template with `ip`/`date`/`long` mappings, and a Kibana correlation by `th_flow_id`.
- **Microsoft Sentinel:** Azure Monitor Agent/AMA syslog relay or Logs Ingestion API/DCR, custom table with the fields above, and KQL joins on `th_session_id`/`th_flow_id`.

Keep `th_schema_version = 2`. TLS transport and enrichment settings are transport/UI concerns and do not require a schema change. Add optional fields only if they cannot be derived; do not rename existing keys.

## What is already sound

- Syslog is disabled by default; boot resume requires both `startAtBoot` and `captureWanted`.
- No `QUERY_ALL_PACKAGES`; package visibility is limited to launcher queries.
- Syslog payloads exclude payload bytes, URLs, DNS names, country/org labels, and app labels.
- Syslog header fields are sanitised; JSON is escaped; MSGID is constrained.
- Queue is bounded, with token-bucket rate limiting, exponential backoff, and jitter.
- No flow metadata is written to logcat; only two generic VPN-establishment warnings exist.
- The VPN service is non-exported and protected by `BIND_VPN_SERVICE`; Settings/About are non-exported.
- Helper sockets are network-bound by design, and forwarded sockets are protected; the caveats are null-network and ignored `protect()` results.
- IPv4 header/packet construction and checksum math are correct, and sequence wrap arithmetic is handled carefully.
- DNS parser has good high-level guards (response bit, rcode, count caps, pointer bounds, hop cap), apart from the field-level bounds gap.
- `TrafficTracker` is consistently synchronized; session-map creation uses a correct double-checked pattern.
- No third-party runtime dependencies; no packet payload is collected.

## Known limitations / assumptions

- IPv6 is parsed but not forwarded; v1.0 routes IPv4 only.
- DNS names are visible only for plaintext DNS on port 53; DoH/DoT is opaque.
- Syslog and enrichment are cleartext in v1.0; v1.1 must change this.
- No pcap/pcapng, payload inspection, firewall, companion addon, or root mode.
- History encryption is not implemented; app sandbox and `allowBackup=false` are the current boundary.
- Only one physical Android 16 device was connected during this audit.
